Level 3——回头补 Java 本身

这是你后面很容易遇到的一个问题：Spring Boot 会让人感觉“Java 会了”，因为大量事情都被框架做掉了。

比如你会写：

@RestController
@Service
@Mapper
@Transactional

但中级 Java 后端还需要理解这些代码下面依赖的 Java 基础。

重点补：

Java核心
├── 面向对象
│   ├── 继承
│   ├── 多态
│   ├── 接口
│   └── 抽象类
│
├── 集合
│   ├── ArrayList
│   ├── LinkedList
│   ├── HashMap ★
│   ├── HashSet
│   └── ConcurrentHashMap
│
├── 泛型 ★
│
├── 异常体系
│
├── Stream / Lambda
│
├── IO
│
└── 反射 / 注解

尤其是反射、注解、动态代理。

你之前一直在问：

注解到底是什么？为什么加个注解 Spring 就知道该干什么？

等你把这些东西学起来，会慢慢串成：

Java注解
+
反射
+
动态代理
+
IOC
+
AOP
↓
Spring为什么能这么干

到这里，Spring 才会逐渐从“很多神奇注解”变成一个你能解释的框架。

Level 4——数据库从“会写 SQL”升级到“懂 SQL”

你现在数据库阶段更接近：

我能不能把我要的数据查出来？

以后要逐渐变成：

这条 SQL 为什么这么执行？数据量上来以后还快不快？并发时数据会不会错？

重点：

MySQL
├── 索引 ★★★★★
│   ├── B+ Tree
│   ├── 联合索引
│   ├── 最左匹配
│   ├── 覆盖索引
│   └── 索引失效
│
├── EXPLAIN ★★★★
│
├── 事务 ★★★★★
│   ├── ACID
│   ├── 隔离级别
│   ├── 脏读
│   ├── 不可重复读
│   └── 幻读
│
├── MVCC
│
├── 锁
│   ├── 行锁
│   ├── 表锁
│   ├── 乐观锁
│   └── 悲观锁
│
└── SQL优化

比如你现在看到：

SELECT *
FROM articles
WHERE author_id = ?
ORDER BY created_at DESC;

首先考虑的是“能不能查”。

以后看到同一条 SQL，你脑子里应该开始出现：

author_id有没有索引？

1000万条数据怎么办？

(author_id, created_at)要不要联合索引？

EXPLAIN显示走了什么索引？

为什么走这个索引？

分页到第100000页怎么办？

这就是后端能力开始往中级走的一个明显变化。

@PostMapping("/buy")

1000个人同时访问，就可能出现：

库存只有1

这时候你再去学：

并发

数据库锁

就不会觉得它们是凭空冒出来的一堆概念，而是知道它们分别在解决什么问题。

Java 后端做到中级以后，JVM 绕不开，但你暂时不需要钻得特别深。

先掌握：

JVM

├── 对象生命周期
├── GC

Level 7——再深入 Spring 原理

这时候再回头深入 Spring，会比现在直接硬啃源码容易得多。

你现在的问题可能还是：

@Component到底怎么工作的？

@Autowired为什么能注入？

@Transactional为什么加一个注解就能开启事务？

后面系统学：

Spring
├── IOC
├── Bean生命周期
├── DI
├── AOP
├── 动态代理
├── BeanPostProcessor
├── 循环依赖
├── Spring MVC执行流程
└── Spring Boot自动配置

最终你要能解释这样的代码：

@Transactional
public void createArticle() {
}

为什么你没有手写：

begin();

try {
...
commit();
} catch (...) {
rollback();
}

Spring 却能帮你完成事务。

最后这条链能串起来：

@Transactional注解
↓
Spring识别
↓
Bean
↓
AOP
↓
动态代理
↓
代理对象
↓
开启事务
↓

↓
提交 / 回滚

到这一步，你就不只是“会用 Spring”。

Level 8——换一个比 RealWorld 更复杂的项目

RealWorld 非常适合你现在练基本功，但它后面有一个限制：

业务比较简单，并发和数据一致性场景不够多。

所以 RealWorld 完成以后，我更建议第二个项目做一个简化的：

商城 / 订单系统

用户
商品
库存
购物车

优惠券

因为它天然会出现：

下单
↓

↓

↓

↓

紧接着问题就来了：

扣了库存，订单创建失败怎么办？

订单成功，支付失败怎么办？

用户连续点10次支付怎么办？

两个人同时抢最后一个商品怎么办？

Redis和MySQL数据不一致怎么办？

MQ消息发送失败怎么办？

同一条消息被消费两次怎么办？

这些问题会自然把你带到：

Redis高级
RabbitMQ / Kafka
幂等

限流

最终一致性

你以前在 Express 里已经碰过 INSERT IGNORE 和幂等。到了这个阶段，你会发现：

INSERT IGNORE 只是实现某些幂等场景的一种手段，真正的“幂等”是系统设计问题。
