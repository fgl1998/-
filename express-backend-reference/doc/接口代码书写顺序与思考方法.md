# Express + TypeScript 接口代码书写顺序与思考方法

这份文档只解决一个问题：

> 当你准备写一个新接口时，第一行应该写什么，后面按什么顺序继续，怎样避免写到一半才发现前面的类型和依赖没有准备好。

本文使用“创建用户”作为贯穿示例，技术栈是 Express、TypeScript、MySQL、mysql2 和手写 SQL。不要求 Service 必须使用 class，示例优先使用更直观的工厂函数完成依赖注入。

---

## 1. 先区分三种顺序

初学者最容易把“思考顺序”“书写顺序”和“运行顺序”混在一起。它们不是同一个顺序。

### 1.1 思考顺序：先想接口要完成什么

```text
接口目标
  → 输入是什么
  → 业务规则是什么
  → 需要哪些数据库操作
  → 成功返回什么
  → 可能怎样失败
```

### 1.2 书写顺序：先写被别人依赖的代码

```text
类型
  → 数据库行类型和Mapper
  → Repository契约
  → Repository实现
  → Service
  → 组装依赖
  → 请求校验
  → Route
  → 错误中间件
```

### 1.3 运行顺序：请求从外向内执行

```text
HTTP请求
  → Route
  → 请求校验
  → Service
  → Repository
  → MySQL
  → Repository
  → Service
  → HTTP响应
```

写代码时不要按照请求运行顺序直接从 Route 往下硬写。这样很容易在 Route 中先写出：

```ts
await userService.create(input)
```

然后才发现：

```text
userService还没创建
userRepository还没创建
Repository契约还没定义
User类型还没定义
```

最容易落笔的规则是：

> A 使用 B，就先把 B 的类型、定义和创建方式准备好，再写 A。

---

## 2. 每写一个接口，先填写“接口需求卡”

不要一看到需求就打开 Route 写代码。先用中文把下面这张卡填写完整。

### 2.1 空白模板

```text
接口名称：
HTTP方法和路径：

输入：

输入校验：

业务规则：

需要的数据库操作：

成功输出：

可能失败：
```

### 2.2 创建用户示例

```text
接口名称：创建用户
HTTP方法和路径：POST /users

输入：
name、email

输入校验：
name必须是2到50个字符
email必须符合邮箱格式
email统一转成小写

业务规则：
相同email不能创建两次

需要的数据库操作：
按email查询用户
插入用户
按新生成的ID读取用户

成功输出：
id、name、email、createdAt

可能失败：
请求参数错误
邮箱已经存在
数据库执行失败
插入成功后没有读到记录
```

接口需求卡的作用是把问题拆开。后面的每一层都只负责卡片中的一部分。

---

## 3. 第一步：先写输入、实体和输出类型

这一阶段不要写 SQL，也不要写 Express。

### 3.1 Service输入

```ts
interface CreateUserInput {
  name: string
  email: string
}
```

它回答：

```text
创建用户这个业务用例需要什么数据？
```

### 3.2 内部业务实体

```ts
interface User {
  id: number
  name: string
  email: string
  createdAt: Date
}
```

它回答：

```text
程序内部怎样表示一个用户？
```

### 3.3 API输出

```ts
interface UserOutput {
  id: number
  name: string
  email: string
  createdAt: string
}
```

它回答：

```text
返回给前端的用户是什么形状？
```

为什么 `User.createdAt` 是 `Date`，`UserOutput.createdAt` 是 `string`：

```text
程序内部适合使用Date进行时间操作
JSON响应中时间最终会变成字符串
```

完成这一步后，先看编辑器是否有类型错误。不要急着写下一层。

---

## 4. 第二步：根据SELECT语句写数据库行类型

先确定 Repository 将要执行的查询：

```sql
SELECT id, name, email, created_at
FROM users
WHERE email = ?
LIMIT 1
```

SQL 选择了四列，所以定义：

```ts
interface UserRow extends RowDataPacket {
  id: number
  name: string
  email: string
  created_at: Date
}
```

固定思考方法：

```text
先看SELECT写了哪些列
        ↓
再给UserRow写相同字段
        ↓
字段类型根据当前数据库字段和mysql2配置确定
```

不要为了“生产级”提前写不必要的联合类型。当前配置确认返回 `number` 和 `Date`，就先写：

```ts
id: number
created_at: Date
```

只有数据库使用 BIGINT、`dateStrings` 等配置时，再考虑：

```ts
id: number | string
created_at: Date | string
```

---

## 5. 第三步：先写Mapper，隔开数据库模型和业务模型

数据库字段是：

```ts
created_at
```

业务字段是：

```ts
createdAt
```

所以先写转换函数：

```ts
function toUser(row: UserRow): User {
  return {
    id: row.id,
    name: row.name,
    email: row.email,
    createdAt: row.created_at
  }
}
```

Mapper只回答：

```text
数据库行怎样变成业务实体？
```

Mapper不执行 SQL、不检查邮箱是否重复，也不返回 HTTP 响应。

---

## 6. 第四步：根据Service的需要定义Repository契约

回到接口需求卡：

```text
需要按email查重
需要创建用户
```

所以 Service 需要的 Repository 能力是：

```ts
interface UserRepository {
  findByEmail(email: string): Promise<User | null>
  create(input: CreateUserInput): Promise<User>
}
```

不要按照数据库表有多少字段，就给 Repository 写多少方法。正确方法是：

```text
Service需要什么数据库能力
        ↓
Repository契约才提供什么方法
```

如果 `findById` 只在 MySQL Repository 内部用于“插入后回查”，可以把它留在具体实现内部，不一定暴露给 Service 契约。

---

## 7. 第五步：创建Pool，然后实现Repository

Repository要执行 SQL，所以必须先有连接池。

### 7.1 创建Pool

```ts
const pool: Pool = mysql.createPool({
  host: process.env.DB_HOST,
  port: Number(process.env.DB_PORT ?? 3306),
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  waitForConnections: true,
  connectionLimit: 10,
  charset: 'utf8mb4',
  timezone: 'Z'
})
```

### 7.2 实现Repository时的内部顺序

先写最简单的查询，再写依赖这个查询的创建操作：

```text
findByEmail
  → findById
  → create
```

原因是 `create` 执行 INSERT 后，需要使用 `findById` 读取完整用户。

### 7.3 Repository中只思考数据库问题

写 `findByEmail` 时只问：

```text
SQL是什么？
参数是什么？
SELECT返回什么类型？
没有数据时返回什么？
怎样转换成User？
```

写 `create` 时只问：

```text
INSERT参数是什么？
怎样取得insertId？
怎样读取刚创建的记录？
MySQL重复键怎样转换成稳定错误？
```

Repository中不要出现：

```ts
req.body
res.status(...)
```

因为 Repository 不负责 HTTP。

完成 Repository 后立即运行：

```powershell
npm run typecheck
```

如果这一层有错误，停在这一层解决，不要带着错误继续写 Service。

---

## 8. 第六步：写Service业务流程

Repository已经存在，Service现在只需要排列业务步骤。

不用class也可以完成依赖注入：

```ts
interface UserService {
  create(input: CreateUserInput): Promise<UserOutput>
}

function createUserService(
  repository: UserRepository
): UserService {
  return {
    async create(
      input: CreateUserInput
    ): Promise<UserOutput> {
      const existingUser =
        await repository.findByEmail(input.email)

      if (existingUser) {
        throw emailAlreadyExistsError()
      }

      const user = await repository.create(input)

      return {
        id: user.id,
        name: user.name,
        email: user.email,
        createdAt: user.createdAt.toISOString()
      }
    }
  }
}
```

Service中的顺序直接来自接口需求卡：

```text
接收可信input
  → 按email查重
  → 已存在则抛业务错误
  → 调用Repository创建
  → 转换成UserOutput
  → 返回
```

Service中不要出现：

```ts
Request
Response
res.status(...)
pool.execute(...)
```

因为 Service 不负责 HTTP，也不负责 SQL。

完成 Service 后再次运行：

```powershell
npm run typecheck
```

---

## 9. 第七步：组装依赖

定义和创建是两件事。

前面完成的是定义：

```text
UserRepository规定需要哪些方法
具体Repository实现这些方法
createUserService规定怎样产生Service
```

现在才真正创建对象：

```ts
const userRepository: UserRepository =
  createMysqlUserRepository(pool)

const userService: UserService =
  createUserService(userRepository)
```

如果 Repository 当前直接使用对象字面量，则组装可以是：

```ts
const userService: UserService =
  createUserService(userRepository)
```

这两行必须放在 Route 前面，因为 Route 要使用 `userService`。

依赖方向：

```text
pool
  ↓ 传给Repository
userRepository
  ↓ 传给Service
userService
  ↓ 被Route调用
```

依赖注入的关键是“从外部传入”，不是“必须使用class”。

---

## 10. 第八步：写HTTP输入校验

现在才处理 `req.body`。

```ts
function parseCreateUserInput(
  body: unknown
): CreateUserInput | null {
  if (
    typeof body !== 'object' ||
    body === null ||
    !('name' in body) ||
    !('email' in body) ||
    typeof body.name !== 'string' ||
    typeof body.email !== 'string'
  ) {
    return null
  }

  const name = body.name.trim()
  const email = body.email.trim().toLowerCase()

  if (name.length < 2 || name.length > 50) {
    return null
  }

  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
    return null
  }

  return { name, email }
}
```

它完成：

```text
unknown
  → 检查对象结构
  → 检查字段类型
  → trim和邮箱小写化
  → 检查业务允许的格式
  → CreateUserInput或null
```

校验通过后，Service不再处理 `unknown`。

---

## 11. 第九步：最后写Route

此时Route依赖的所有内容都已经存在：

```ts
app.post('/users', async (req, res, next) => {
  try {
    const input = parseCreateUserInput(req.body)

    if (!input) {
      res.status(400).json({
        success: false,
        code: 'VALIDATION_ERROR',
        message: '请求参数错误'
      })
      return
    }

    const user = await userService.create(input)

    res.status(201).json({
      success: true,
      code: 'USER_CREATED',
      message: '用户创建成功',
      data: user
    })
  } catch (error) {
    next(error)
  }
})
```

Route只做四件事：

```text
读取HTTP输入
  → 校验
  → 调用Service
  → 发送HTTP响应
```

Route中不要重新查数据库，也不要再次实现邮箱查重。

---

## 12. 第十步：错误中间件和启动放在最后

Express代码的末尾顺序固定为：

```text
所有正常Route
  → 404中间件
  → 错误处理中间件
  → app.listen
```

最小排列：

```ts
app.post('/users', createUserHandler)

app.use(notFoundHandler)

app.use(errorHandler)

app.listen(port, () => {
  console.log(`服务已启动：http://localhost:${port}`)
})
```

错误中间件放在 Route 前面时，后面的 Route 错误无法按预期进入它。

## 13. 单文件app.ts的固定排列模板

写单文件学习项目时，文件从上到下固定排列为：

```text
1. import

2. 输入类型
   CreateUserInput

3. 内部实体和输出类型
   User
   UserOutput

4. 数据库行类型
   UserRow

5. Repository和Service契约
   UserRepository
   UserService

6. 业务错误
   EmailAlreadyExistsError

7. Mapper
   toUser

8. 数据库连接池
   pool

9. Repository实现
   userRepository

10. Service定义和依赖组装
    createUserService
    userService

11. HTTP输入校验
    parseCreateUserInput

12. Route
    app.post('/users', ...)

13. 404和错误中间件

14. app.listen
```

这个顺序不是唯一正确的代码风格，但它特别适合初学者，因为大多数名字在被使用以前已经出现。

## 14. 不要一次写完整接口：使用五个检查点

### 检查点一：类型完成

应该已经有：

```text
CreateUserInput
User
UserOutput
UserRow
UserRepository
```

执行：

```powershell
npm run typecheck
```

### 检查点二：Repository完成

检查：

```text
SELECT使用UserRow[]
INSERT使用ResultSetHeader
SQL参数使用?
数据库行通过Mapper转成User
```

再次执行：

```powershell
npm run typecheck
```

### 检查点三：Service完成

检查：

```text
Service通过参数接收Repository
Service没有导入Express
Service没有执行SQL
Service返回UserOutput
```

再次执行类型检查。

### 检查点四：Route完成

检查：

```text
req.body先校验
Route调用userService
Route没有直接调用userRepository
错误交给next(error)
```

再次执行类型检查。

### 检查点五：完整请求

启动服务：

```powershell
npm run dev
```

然后使用 Postman 或其他HTTP客户端验证：

```text
合法数据能够创建
非法name返回400
非法email返回400
重复email返回409
数据库中确实增加记录
响应不包含数据库内部字段
```

## 15. 写到一半卡住时怎样判断下一步

### 情况一：出现“某变量从哪里来”

例如：

```ts
userService.create(input)
```

立即向上追问：

```text
userService在哪里创建？
创建它需要什么？
它依赖的userRepository在哪里创建？
userRepository依赖的pool在哪里创建？
```

如果找不到来源，说明依赖组装步骤还没有完成。

### 情况二：TypeScript说参数是any

例如：

```ts
async findByEmail(email) {}
```

检查：

```text
对象是否标注了UserRepository类型？
参数是否写了email: string？
方法是否写了Promise<User | null>？
```

### 情况三：mysql2结果不能读取rows[0]

检查SELECT是否写了：

```ts
execute<UserRow[]>()
```

以及：

```ts
interface UserRow extends RowDataPacket
```

### 情况四：insertId不存在

检查INSERT是否写了：

```ts
execute<ResultSetHeader>()
```

### 情况五：Route越来越长

把代码按责任检查：

```text
SQL移入Repository
业务判断移入Service
输入类型和格式检查保留在HTTP边界
```

## 16. 新接口通用书写清单

以后新增任何接口，都可以复制下面的清单逐项完成：

```text
[ ] 1. 用中文写清接口目标
[ ] 2. 写HTTP方法和路径
[ ] 3. 列出输入字段
[ ] 4. 列出输入校验规则
[ ] 5. 列出业务规则
[ ] 6. 列出需要的数据库操作
[ ] 7. 列出成功输出
[ ] 8. 列出可能失败

[ ] 9. 定义Input类型
[ ] 10. 定义内部Entity类型
[ ] 11. 定义Output类型
[ ] 12. 根据SELECT定义Row类型
[ ] 13. 编写Row到Entity的Mapper
[ ] 14. 定义Repository契约
[ ] 15. 实现Repository
[ ] 16. 运行typecheck
[ ] 17. 编写Service
[ ] 18. 注入Repository并创建Service
[ ] 19. 运行typecheck
[ ] 20. 编写HTTP输入校验
[ ] 21. 编写Route
[ ] 22. 编写或复用错误处理
[ ] 23. 运行typecheck
[ ] 24. 启动服务完成真实请求测试
```

## 17. 最后记住三句话

第一句：

```text
谁被别人使用，谁就先写。
```

第二句：

```text
Repository写数据库，Service写业务，Route写HTTP。
```

第三句：

```text
每完成一层就typecheck，不要把所有错误留到最后。
```

当单文件版本能够正确运行后，再按照 Service、Repository、Controller、Route 的职责机械拆分文件。不要在接口流程还没写通时，同时学习分层、拆文件、复杂泛型和依赖注入容器。
